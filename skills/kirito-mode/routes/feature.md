# Route: feature

New behaviour or a design change across modules. Spec first, then a plan, then test-first code.

0. **Too big?** Check the Signals in `SKILL.md`: a task too big and foggy for one session goes to `/wayfinder` first, then each resolved slice runs through this route.
1. **Ground (optional).** If the area is unfamiliar, run `how` on it so the interview starts from facts.
2. **Grill.** Run `grill-with-docs`. It interviews the user one round at a time and records terms in `GLOSSARY.md` and decisions in ADRs. If a question needs a runnable answer (state, business logic, a UI to see), run `prototype`, then bring the answer back. Keep steps 2-5 in one context window.
3. **Spec.** Run `to-spec`. It writes `docs/specs/<feature>.md` with `Status: draft` and asks the user to confirm the test seams. Then run `flow-map` in planned mode: it adds a `## Flows` section with the business flow, data flow, and UI journey the feature needs, so the user approves the picture with the words. Wait for the user to approve the spec. Do not start tickets on a draft.
4. **Design (optional).** If the work crosses a module boundary or adds an interface, run `architect` and keep its sketch with the spec. If the design is contested (several valid shapes, an interface other code will depend on, or a choice that is costly to undo), run `interrogate` on the sketch before you write tickets. It dispatches one fresh adversary in a worktree; address each verified finding before you write tickets, and show the user the Dropped summary. Skip it for routine designs.
5. **Plan.** Run `to-tickets`. It writes `docs/plans/<feature>/NN-<slug>.md`, one vertical slice per file, with blocking edges. Write each ticket so a fresh session can do it cold: a reader with no memory of this conversation must be able to start. Wait for the user to approve the breakdown.
   **Boundary.** Once the breakdown is approved and the session is on Opus, STOP with one message telling the user to run `/clear`, `/model` Sonnet 5.5, then `/kirito-mode [--delegate] feature <plan dir>` (the plan directory's path). Do not switch models in this context. A session already on Sonnet continues to step 6.
6. **Implement.** Started either after the step 5 boundary (`feature <plan dir>`: read the spec and tickets in that directory, do not re-explore) or directly in a Sonnet session. For each ticket, blockers first:
   - Default: run `tdd` inline at the seams agreed in the spec.
   - Delegate mode (see `SKILL.md` section 2): the main session runs Sonnet 5.5 from the step 5 boundary; later spec, plan, or ticket writing means a new session on Opus 5.5. Dispatch one fresh `implementer` per ticket with a new `Agent` call, the ticket and spec paths, and the ticket's `Model:` value as the `model` override (a ticket without a `Model:` line gets no override, so the agent's Sonnet default applies). The `reviewer` is the one that never takes a `model` override. Never resume an earlier implementer with `SendMessage`. Then read its diff and rerun the ticket's tests and typecheck yourself. Settle any conflict it hands back with the user before the next ticket.
   - **Escalation (the only definition; other skills point here).** A `haiku` ticket whose implementer hands back failing checks twice, or that draws a `must-fix` in review, is re-dispatched ONCE on Sonnet (`model: sonnet`) with the previous hand-back and the findings in the prompt. Write `Escalated: haiku → sonnet (<reason>)` in the ticket and a note in the review log. Every later fix for that ticket also runs on Sonnet.

   Mark the ticket `Status: done` when its acceptance criteria pass. Run typecheck between tickets and the full suite after the last. On a long feature, suggest `/clear` between tickets, since each ticket is self-contained. For long or unattended work, keep a decision log with `show-me-your-work`.
7. **Finish.** Follow the Finish section of `SKILL.md`. Commit per ticket or once per feature, whichever keeps each commit reviewable.
